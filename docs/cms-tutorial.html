纵深防御：按钮能不能显示由前端 Permission 组件决定（体验），接口能不能调用由后端 @PreAuthorize 决定（安全）。前端隐藏只是 UI，后端校验才是底线——因为别人可以直接 curl 你的接口。

3.2 全表统一设计约定

  • 主键：自增 BIGINT id
  • 时间：created_at 默认 CURRENT_TIMESTAMP，updated_at 自动更新
  • 逻辑删除：所有业务表带 deleted TINYINT，删除 = UPDATE 置 1，查询永远 AND deleted = 0。数据不物理消失，可恢复、可审计
  • 字符集：utf8mb4 + utf8mb4_unicode_ci（表情符号也能存）
  • 索引：外键字段建普通索引（如 idx_category_id），不做物理外键约束，避免锁与迁移成本

每个依赖解决什么问题？为什么是它？

spring-boot-starter-* 是一组"开箱即用"的依赖集合——加一个 starter，Spring Boot 就自动装配好对应的组件，不用你手动配置。

  • web：内嵌 Tomcat + Spring MVC，提供 @RestController 等 HTTP 能力。没它，你的接口根本接收不到请求。
  • jdbc：提供 JdbcTemplate。刻意不引入 MyBatis/JPA，因为本项目的核心学习目标就是搞懂数据访问底层：SQL 自己写、结果集自己映射、事务边界自己控制。
  • security：认证授权框架。它是"过滤器链"架构——后面 4.4 会看到我们如何把 JWT 过滤器插进链条。
  • data-redis：Redis 客户端。Refresh Token 本可以放 Redis 实现服务端吊销，本项目先用 JWT 自包含方案（7 天有效期），Redis 留给后续扩展。
  • validation：参数校验。配合 @Valid + DTO 上的 @NotBlank 等注解，Controller 入口自动拦截非法参数，不用手写 if 判断。
  • aop：面向切面编程。操作日志（4.6）靠它实现"零侵入"——业务代码不写一行日志逻辑。

为什么 mysql-connector-j 是 runtime 作用域？因为它只在运行期被 JDBC 驱动加载，编译期代码里从不 import 它。

4.2 统一响应与全局异常

所有接口返回同一结构 { code, message, data }，前端拦截器只要认准 code === 200 即可，业务错误和系统错误处理路径完全统一。

common/response/ApiResponse.javaJAVA
public class ApiResponse<T> {
    private int code;      // 200 成功，其余为业务/系统错误码
    private String message;
    private T data;

    public static <T> ApiResponse<T> success(T data) {
        return new ApiResponse<>(200, "操作成功", data);
    }
    public static <T> ApiResponse<T> error(ResultCode rc) {
        return new ApiResponse<>(rc.getCode(), rc.getMessage(), null);
    }
}
common/exception/GlobalExceptionHandler.javaJAVA
@RestControllerAdvice
public class GlobalExceptionHandler {

    // 业务异常：Service 层主动抛出，如"文章不存在"
    @ExceptionHandler(BusinessException.class)
    public ApiResponse<Void> handleBusiness(BusinessException e) {
        return ApiResponse.error(e.getResultCode());
    }

    // 参数校验失败：@Valid 触发
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ApiResponse<Void> handleValid(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
                .map(f -> f.getField() + ": " + f.getDefaultMessage())
                .collect(Collectors.joining("; "));
        return ApiResponse.error(ResultCode.PARAM_ERROR, msg);
    }

    // 兜底：未知异常不把堆栈泄漏给前端
    @ExceptionHandler(Exception.class)
    public ApiResponse<Void> handleUnknown(Exception e) {
        log.error("Unknown error", e);
        return ApiResponse.error(ResultCode.SYSTEM_ERROR);
    }
}
@RestControllerAdvice 是什么？为什么它能"接住"所有异常？

@RestControllerAdvice = @ControllerAdvice + @ResponseBody 的合体，作用是：全局拦截 Controller 抛出的异常，统一转成 JSON 响应。它是 Spring MVC 的"异常总出口"——任何接口抛异常，框架先看有没有匹配的 @ExceptionHandler 方法，有就用它兜住，没有才返回默认错误页（HTML 的 500 页面）。

三个方法的匹配优先级：Spring 按异常类型从具体到宽泛匹配。抛 BusinessException → 走第一个；@Valid 校验失败 → 走第二个；其他任何异常 → 走第三个兜底。

  • @ExceptionHandler(BusinessException.class)：BusinessException 是 Service 层主动抛的业务错误（如"文章不存在"），带明确的 ResultCode，直接翻译成对应 code/message。
  • @ExceptionHandler(MethodArgumentNotValidException.class)：@Valid 校验失败时抛的异常类型。getFieldErrors() 能拿到所有校验失败的字段和提示，拼成一条可读的错误信息——这就是为什么参数错误能精确到"username: 不能为空"。
  • @ExceptionHandler(Exception.class)：最后防线。打日志排查，但绝不让堆栈泄漏给前端——对外只返回"系统繁忙"，防止攻击者从报错信息反推系统结构。

不写这个类的后果：任何一个未捕获异常都会返回 Spring 默认的 HTML 错误页，前端根本没法统一处理，报错信息还可能暴露内部细节。

4.3 JWT 双 Token 签发与解析

用的是 jjwt 0.12 的链式 API。两个 Token 共用一套生成逻辑和密钥，只有 type claim 和过期时间不同，过滤器里靠这个区分 Access 和 Refresh。

security/JwtTokenProvider.java（核心）JAVA
@Component
public class JwtTokenProvider {

    @Value("${jwt.secret}") private String secret;
    @Value("${jwt.access-token-expiration}") private long accessExp;
    @Value("${jwt.refresh-token-expiration}") private long refreshExp;

    private SecretKey key;

    @PostConstruct
    public void init() {
        this.key = Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
    }

    public String generateAccessToken(Long userId, String username) {
        return generateToken(userId, username, accessExp, "ACCESS");
    }

    public String generateRefreshToken(Long userId, String username) {
        return generateToken(userId, username, refreshExp, "REFRESH");
    }

    private String generateToken(Long userId, String username, long expiration, String type) {
        Map<String, Object> claims = new HashMap<>();
        claims.put("userId", userId);
        claims.put("type", type);

        return Jwts.builder()
                .claims(claims)
                .subject(username)          // 标准字段：用户名
                .issuedAt(new Date())
                .expiration(new Date(System.currentTimeMillis() + expiration))
                .signWith(key)              // HS 系列，密钥自动匹配算法
                .compact();
    }

    public Claims parseToken(String token) {
        return Jwts.parser().verifyWith(key).build()
                .parseSignedClaims(token).getPayload();
    }
}
这个类上的三个注解分别是什么？
  • @Component：把当前类注册为 Spring 容器管理的 Bean（单例）。声明之后，其他类用构造器注入 private final JwtTokenProvider jwtTokenProvider 就能直接拿到实例，不需要自己 new。它和 @Service、@Repository、@Controller 功能等价，只是语义不同——那些是 @Component 的"带语义的别名"，后面 4.5 会看到。
  • @Value("${jwt.secret}")：把 application.yml 里 jwt.secret 的值注入到这个字段。配置外置的好处：改密钥、改过期时间不用改代码，生产环境还能用环境变量覆盖（${JWT_SECRET:默认值} 的写法）。
  • @PostConstruct：Spring 生命周期注解——Bean 构造完成、依赖注入完成后自动执行一次 init()。这里把字符串密钥转成 SecretKey 对象。为什么不在构造方法里做？因为 @Value 注入发生在构造之后，构造方法里读 secret 还是 null。

为什么 key 只初始化一次？JWT 签名/验签是高频操作，如果每次调用都重新算 key 就是浪费。单例 Bean + @PostConstruct 保证进程生命周期内只有一份 key。

为什么两个 Token 共用同一个密钥？Access 和 Refresh 用同一套签发逻辑，只是 type claim（"ACCESS"/"REFRESH"）和过期时间不同。解析时先看 type 就知道它是哪种 Token，这在 4.4 的过滤器里是判断"是否允许自动刷新"的依据。共用密钥也简化了配置——一套 jwt.secret 就够了。

4.4 安全过滤链：无状态 + 过滤器鉴权

无状态会话（STATELESS）意味着服务端不存 Session，每次请求都靠 JWT 自证身份。核心就两个文件：SecurityConfig 定义放行规则和过滤器位置；JwtAuthenticationFilter 在每个请求进来时解析 Token、把身份塞进 SecurityContext。

config/SecurityConfig.javaJAVA
@Configuration
@EnableWebSecurity
@EnableMethodSecurity(prePostEnabled = true)   // 开启 @PreAuthorize 注解
public class SecurityConfig {

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();     // BCrypt 加盐哈希
    }

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf(AbstractHttpConfigurer::disable)   // 无状态 API，不需要 CSRF
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()
                .requestMatchers("/auth/login", "/auth/refresh").permitAll()
                .requestMatchers("/doc.html", "/v3/api-docs/**").permitAll()
                .anyRequest().authenticated()         // 其余全部要登录
            )
            .exceptionHandling(ex -> ex
                .authenticationEntryPoint(jwtAuthenticationEntryPoint)  // 401
                .accessDeniedHandler(jwtAccessDeniedHandler))           // 403
            .addFilterBefore(jwtAuthenticationFilter,
                    UsernamePasswordAuthenticationFilter.class);        // 插队
        return http.build();
    }
}
SecurityConfig 上的三个注解 + @Bean 是什么？
  • @Configuration：告诉 Spring"这个类是配置类"，里面的 @Bean 方法会被执行并把返回值注册进容器。没有它，filterChain 方法根本不会被调用。
  • @EnableWebSecurity：开启 Spring Security 的 Web 安全支持，加载它内置的一整条过滤器链（默认十几二十个过滤器：CorsFilter、CsrfFilter、AuthorizationFilter……）。我们的 JWT 过滤器就是插进这条链的。
  • @EnableMethodSecurity(prePostEnabled = true)：开启方法级权限注解。开了它，@PreAuthorize("hasAuthority('article:update')") 才生效——这是 RBAC 在接口上落地的开关，忘写这个注解，所有 @PreAuthorize 都会静默失效（这是非常隐蔽的坑）。
  • @Bean：把方法返回值注册为容器 Bean。PasswordEncoder 是 Security 认证流程要用到的密码校验器，filterChain 返回的 SecurityFilterChain 是整个安全配置的产物。
三行关键配置，为什么这么写？
  • csrf disable：CSRF 防护针对"基于 Cookie 的会话"——攻击者伪造表单让浏览器自动带上你的 Cookie。而本项目用 JWT，Token 存在 JS 变量里由前端手动放入 Header，攻击者无法伪造，所以 CSRF 没有意义，关掉。
  • STATELESS：明确告诉 Security"服务端不存 Session，不创建、不使用 HttpSession"。每个请求都是独立的，身份全靠 JWT 自证。这才能支撑水平扩展——多个后端实例之间无需同步 Session。
  • addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class)：把自定义过滤器插到"用户名密码认证过滤器"之前。因为我们是无状态 JWT，不需要 UsernamePasswordAuthenticationFilter 去走表单登录流程——我们的过滤器先解析 Token，能解析出身份就直接放行，解析不出再交给后续逻辑（最终返回 401）。"插队"的位置决定了执行顺序。
@PreAuthorize 用法：方法上加 @PreAuthorize("hasAuthority('article:update')")。权限字符串就是 sys_menu 表里按钮行的 permission 字段，登录时后端按角色把权限码查出来塞进用户的 authorities 里，两边对得上。这一行注解 = 接口级权限校验，是 RBAC 落地的最后一环。

4.5 业务模块：标准四层开发范式

用户/角色/菜单/分类/文章/通知这些模块都是同一套四层结构。下面以文章为例，走完一个完整的 CRUD，其他模块照搬即可。

① Repository：纯 SQL，手写映射

article/repository/ArticleRepository.javaJAVA
@Repository
public class ArticleRepository {

    private final JdbcTemplate jdbcTemplate;

    // RowMapper：把 ResultSet 一行映射为实体（也可用 BeanPropertyRowMapper，这里手写更可控）
    public static final RowMapper<Article> MAPPER = (rs, rowNum) -> {
        Article a = new Article();
        a.setId(rs.getLong("id"));
        a.setTitle(rs.getString("title"));
        // ... 逐字段映射
        return a;
    };

    public Optional<Article> findById(Long id) {
        String sql = "SELECT ... FROM cms_article WHERE id = ? AND deleted = 0";
        List<Article> list = jdbcTemplate.query(sql, MAPPER, id);
        return list.isEmpty() ? Optional.empty() : Optional.of(list.get(0));
    }

    // 新增：GeneratedKeyHolder 拿回自增主键
    public Long insert(Article article) {
        KeyHolder kh = new GeneratedKeyHolder();
        jdbcTemplate.update(conn -> {
            PreparedStatement ps = conn.prepareStatement(INSERT_SQL,
                    Statement.RETURN_GENERATED_KEYS);
            ps.setString(1, article.getTitle());
            // ... 注意：可空字段做 null 兜底，否则 NOT NULL 列直接报错
            ps.setString(4, article.getCover() != null ? article.getCover() : "");
            return ps;
        }, kh);
        return kh.getKey().longValue();
    }

    // 更新：同样对可空字段做 null -> "" 兜底
    public int update(Article article) {
        return jdbcTemplate.update(UPDATE_SQL,
                article.getTitle(),
                article.getSummary()  != null ? article.getSummary()  : "",
                article.getContent()  != null ? article.getContent()  : "",
                article.getCover()    != null ? article.getCover()    : "",
                article.getCategoryId() != null ? article.getCategoryId() : 0,
                article.getSeoTitle() != null ? article.getSeoTitle() : "",
                article.getSeoDescription() != null ? article.getSeoDescription() : "",
                article.getId());
    }

    // 逻辑删除：deleted = 1
    public int softDelete(Long id) {
        return jdbcTemplate.update(
            "UPDATE cms_article SET deleted = 1, updated_at = NOW() WHERE id = ?", id);
    }
}
@Repository 是什么？为什么要它？

@Repository 是 Spring 给"数据访问层"的专用注解，功能上等价于 @Component，但多一层含义：它让 Spring 把 JdbcTemplate 抛出的 SQL 异常自动翻译成 Spring 的 DataAccessException 体系（统一异常处理时更好接），并且语义上告诉读代码的人"这是数据层"。

为什么 Repository 里全是手写 SQL + 手写 RowMapper？这正是项目"零 ORM"的核心。JdbcTemplate 只做三件事：准备连接、执行 SQL、按 RowMapper 映射结果。每一步都透明可控：

  • jdbcTemplate.query(sql, MAPPER, args) —— ? 占位符由参数填充，天然防 SQL 注入（PreparedStatement 机制），永远不要用字符串拼接 SQL。
  • RowMapper：ResultSet 的每一行调一次，手动把列值 set 进实体。字段名对应关系完全由你掌控，不怕数据库改名、字段增减。
  • Optional<Article> 返回值：强迫调用方处理"查不到"的情况，避免返回 null 后 NPE。配合 orElseThrow 让"数据不存在"的语义非常明确。
  • GeneratedKeyHolder：MySQL 自增主键在执行 insert 后不会自动回填到实体里，需要 RETURN_GENERATED_KEYS 让驱动把生成的主键带回来。这是手写 SQL 最容易忽略的细节——忘了它，新增后你就拿不到新记录的 id。
  • null 兜底（cover != null ? cover : ""）：数据库列是 NOT NULL，而前端/调用方可能不传可选字段。insert 和 update 都要兜底，否则直接报 Column 'cover' cannot be null——这是本项目的真实踩坑（见第 7 章）。

② Service：业务规则 + 事务 + 组装 VO

article/service/ArticleService.java（结构）JAVA
@Service
@RequiredArgsConstructor
public class ArticleService {

    private final ArticleRepository articleRepository;
    private final CategoryRepository categoryRepository;

    // 分页：Repository 只查一页，Service 补全分类名等展示字段
    public PageResult<ArticleVO> getPage(String keyword, Long categoryId,
                                          String status, int page, int pageSize) {
        int offset = (page - 1) * pageSize;
        List<Article> list = articleRepository.findPage(keyword, categoryId, status, offset, pageSize);
        long total = articleRepository.count(keyword, categoryId, status);
        return PageResult.of(list.stream().map(a -> toVO(a)).toList(),
                total, page, pageSize);
    }

    @Transactional                    // 写操作挂事务
    public Long create(ArticleCreateDTO dto) {
        Article article = new Article();
        // DTO -> Entity 手工映射（不装 MapStruct，直白可控）
        article.setTitle(dto.getTitle());
        article.setStatus(dto.getStatus() != null ? dto.getStatus() : "DRAFT");
        // 从 SecurityContext 拿当前登录人，自动填充作者
        Long userId = SecurityUtils.getCurrentUserId();
        article.setAuthorId(userId);
        return articleRepository.insert(article);
    }
}
@Service / @RequiredArgsConstructor / @Transactional 分别是什么？
  • @Service：业务层注解（@Component 的语义别名）。Spring 扫描到它就会实例化并放进容器。Controller 通过构造器注入拿到 Service 实例。
  • @RequiredArgsConstructor：Lombok 注解，为所有 final 字段自动生成构造器。配 private final ArticleRepository articleRepository，Spring 就能"构造器注入"依赖——好处是依赖关系不可变、强制在创建时提供，也方便单元测试。这是 Spring 官方推荐的注入方式（对比字段上 @Autowired 的写法，后者反射注入、测试麻烦）。
  • @Transactional：声明式事务。方法里所有数据库操作（可能多次 update/insert）要么全部成功提交、要么全部回滚。比如"创建文章 + 更新分类计数"两个操作，第二个失败时第一个也会回滚，数据不会半途而废。@Transactional 标注在 public 方法上，Spring 用 AOP 在方法前后自动开启/提交/回滚事务，业务代码里没有一行事务代码。

为什么 Service 里做"DTO → Entity"手工映射？Controller 收到的是前端传来的 DTO（可能缺字段、可能带不该传的字段），Repository 需要的是 Entity。手工逐字段 set 虽然啰嗦，但字段流转完全透明：哪些字段允许客户端传、哪些字段由服务端自己填（比如 authorId 从登录态拿，绝不信前端传的），一眼就能看出来。装 MapStruct 之类的映射库，代码省了但流程变黑盒，不符合本项目"直白可控"的原则。

SecurityUtils.getCurrentUserId() 从哪拿人？认证过滤器把登录用户塞进了 SecurityContext（线程本地），这里取出来填充作者。这样作者信息永远来自可信的登录态，而不是请求参数。

③ Controller：薄薄的 HTTP 层

article/controller/ArticleController.java（结构）JAVA
@RestController
@RequestMapping("/articles")
@RequiredArgsConstructor
public class ArticleController {

    private final ArticleService articleService;

    // 权限码 = 按钮级控制；编辑、发布、删除各自独立
    @PreAuthorize("hasAuthority('article:update')")
    @PutMapping("/{id}")
    @OperationLog("编辑文章")
    public ApiResponse<Void> update(@PathVariable Long id,
                                     @Valid @RequestBody ArticleUpdateDTO dto) {
        dto.setId(id);
        articleService.update(dto);
        return ApiResponse.success(null);
    }
}
Controller 上的每个注解，逐个拆开讲
  • @RestController = @Controller + @ResponseBody。声明"这是个接收 HTTP 请求的类"，并且方法返回值直接序列化成 JSON 写进响应体（不经过视图渲染）。所以 return ApiResponse.success(null) 前端收到的就是 {"code":200,"message":"操作成功","data":null}。
  • @RequestMapping("/articles")：类级别路径前缀。类里所有方法的 URL 都拼在它后面，比如下面的 @PutMapping("/{id}") 完整路径就是 /api/articles/{id}（/api 是 context-path 加的）。统一前缀 + 类级路由，URL 结构一目了然。
  • @PreAuthorize("hasAuthority('article:update')")：方法级权限校验。执行前检查当前登录用户的 authorities 里有没有 article:update 这个权限码，没有就抛 403。注意：这行注解是后端真正的权限防线——前端按钮隐藏只是体验，接口级校验才是安全边界，绕过前端直接调接口也会被拦。
  • @PutMapping("/{id}")：声明这是一个 PUT 请求。{id} 是路径变量，由 @PathVariable Long id 绑定——URL 里 /articles/5 中的 5 自动变成 id 参数。
  • @OperationLog("编辑文章")：本项目自定义注解（第 4.6 节讲），切面自动记操作日志。注解名后的字符串就是日志里的操作描述。
  • @Valid：触发 DTO 上的 Bean Validation 校验（如 @NotBlank、@Size）。校验失败抛 MethodArgumentNotValidException，被 4.2 的全局异常处理器接住。
  • @RequestBody：把请求体里的 JSON 反序列化成 DTO。没有它，Spring 不知道从哪取参数——@RequestBody 对应"JSON 体"，@PathVariable 对应"URL 路径"，@RequestParam 对应"查询字符串"，三者要分清。

为什么 Controller 这么"薄"？它只做三件事：接收参数、调 Service、包响应。业务规则（比如"状态 DRAFT 才能删除"）一律放 Service，这样 Controller 可以轻松替换（比如将来加个 RPC 入口），业务逻辑不需要动。

为什么更新要走"先查后改"？Service 里 update() 第一行先 findById，文章不存在直接抛业务异常。这保证幂等语义：更新一个不存在的 id 得到明确错误，而不是静默影响 0 行。

④ 本项目的 Spring 注解速查表（全项目通用）

把上面几节出现的注解汇总成一张表。读代码时遇到任何一个，回来查这张表就够了。

注解作用为什么需要 / 不写会怎样
@Component注册为 Spring 容器管理的 Bean（通用）不写容器里就没有这个对象，注入时直接报 NoSuchBeanDefinitionException
@Service@Component 的业务层语义别名功能相同，但标注业务层让架构分层可读
@Repository@Component 的数据层语义别名，SQL 异常自动翻译数据层异常翻译成 DataAccessException，全局异常才好统一接住
@RestController@Controller + @ResponseBody，返回 JSON不写 @ResponseBody，返回值会被当成视图名去找模板，报 404
@Configuration声明配置类，@Bean 方法生效配置类不注册，整个 Security 配置全部失效

@PostConstruct依赖注入完成后执行一次初始化构造方法里读注入字段是 null，初始化时机错了
@RequiredArgsConstructor(Lombok) 为 final 字段生成构造器配合构造器注入，依赖关系不可变、可测试
@Transactional方法级声明式事务，失败回滚多步写操作中途失败会产生脏数据（半提交）
@PreAuthorize方法执行前校验权限表达式需要 @EnableMethodSecurity 开启；否则静默失效，接口裸奔
@RestControllerAdvice全局异常处理器异常返回默认 HTML 错误页，前端无法统一处理
@ExceptionHandler指定处理的异常类型按类型匹配，从具体到宽泛，最后一个兜底
@RequestMapping类/方法级 URL 映射（全方法）没有它，请求找不到处理方法，报 404
@GetMapping / @PostMapping / @PutMapping / @DeleteMapping限定 HTTP 方法的 URL 映射不加方法限定，同 URL 的 GET/POST 会冲突或语义混乱
@PathVariable绑定 URL 路径变量（/articles/{id}）路径里的 id 取不到，参数一直是 null
@RequestBodyJSON 请求体反序列化为 DTOSpring 不知道该从哪取参数，直接 400
@Valid触发 DTO 字段校验校验注解（@NotBlank 等）不会自动生效，非法参数直达业务层
@Aspect + @Around声明切面 + 环绕通知操作日志无从拦截，只能在每个方法里手写日志代码
@Slf4j(Lombok) 生成 log 字段手动声明 Logger 实例，样板代码

4.6 AOP 操作日志：注解 + 切面，零侵入

不想在每个方法里手写记日志的代码，就用注解声明、切面统一处理。Controller 方法上加一行 @OperationLog("编辑文章")，环绕通知自动把操作人、方法、参数、耗时、IP 写进 sys_operation_log。

log/aspect/OperationLogAspect.java（核心）JAVA
@Aspect
@Component
public class OperationLogAspect {

    private final LogRepository logRepository;
    private final ObjectMapper objectMapper;

    // 拦截所有标了 @OperationLog 的方法
    @Around("@annotation(operationLog)")
    public Object around(ProceedingJoinPoint pjp, OperationLog operationLog) throws Throwable {
        long start = System.currentTimeMillis();
        Object result = pjp.proceed();            // 先执行业务
        long cost = System.currentTimeMillis() - start;

        try {
            saveLog(pjp, operationLog, cost);
        } catch (Exception e) {
            log.warn("保存操作日志失败: {}", e.getMessage());  // 日志失败不影响主流程
        }
        return result;
    }

    private void saveLog(ProceedingJoinPoint pjp, OperationLog op, long cost) {
        HttpServletRequest request = ((ServletRequestAttributes)
                RequestContextHolder.getRequestAttributes()).getRequest();
        MethodSignature sig = (MethodSignature) pjp.getSignature();

        // 参数序列化为 JSON，超长截断；过滤掉 request/MultipartFile
        String params = buildParams(pjp, sig);

        logRepository.insertOperationLog(
                SecurityUtils.getCurrentUserId(),
                SecurityUtils.getCurrentUsername(),
                request.getMethod(),
                request.getRequestURI(),
                params,
                op.value(),
                getClientIp(request),
                cost);
    }
}
@Aspect / @Around 是什么？AOP 为什么能"零侵入"记日志？

@Aspect：声明这个类是一个切面。切面 = "在哪些方法上（切入点）执行什么逻辑（通知）" 的组合。

@Around("@annotation(operationLog)")：环绕通知，切入点表达式意思是——拦截所有标注了 @OperationLog 注解的方法。方法执行前进入 around()，pjp.proceed() 是"放行，真正执行业务方法"，业务返回后再继续执行日志保存。这就是"环绕"：前后都能插入代码。

关键设计：

  • 切入点用注解而不是包名/方法名：精准——只有主动标了 @OperationLog 的方法才记日志，不想记的不受影响。
  • try-catch 包住日志保存：日志写入失败只打 warn，绝不影响业务本身成功返回。记日志是"锦上添花"，不能因为日志表出问题导致业务报错。
  • pjp.proceed() 之后再记日志：这样能拿到真实耗时（cost），也能拿到业务执行结果。如果是失败场景还能扩展记录异常信息。
  • RequestContextHolder 拿请求：切面方法没有 request 参数，通过 Spring 的线程本地拿到当前请求对象，取 IP、取 URI。

如果不做 AOP：每个 Controller 方法里都要手写"取用户、拼参数、调 insert 日志"，几十个方法重复几十遍，改一个字段要全局改动。AOP 把"横切逻辑"从业务代码里抽走，业务方法保持干净——这就是"零侵入"。

5.2 Axios 封装：Token 注入 + 401 自动刷新

这个文件承担三件事：请求前自动带 Token；响应统一按 code 解包；遇到 401 用 Refresh Token 换新并重放请求。其中有个细节值得注意——并发去重：多个请求同时 401 时，只发一次刷新请求，其他的排队等新 Token。

utils/request.ts（核心）TS
const request = axios.create({
  baseURL: '/api',          // 开发走 Vite proxy，生产走 Nginx
  timeout: 15000,
})

// 请求拦截器：自动带 Token
request.interceptors.request.use(config => {
  const token = getToken()
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})

let isRefreshing = false                 // 刷新互斥锁
let pendingQueue: Array<() => void> = []  // 等待重放的请求

request.interceptors.response.use(
  res => {
    const data = res.data as ApiResponse
    if (data.code === 200) return res
    message.error(data.message || '请求失败')
    return Promise.reject(new Error(data.message))
  },
  async (error) => {
    const original = error.config
    if (error.response?.status === 401 && !original._retry) {
      if (isRefreshing) {
        // 已有刷新在飞：排队等新 Token，然后重放
        return new Promise(resolve => {
          pendingQueue.push(() => {
            original.headers.Authorization = `Bearer ${getToken()}`
            resolve(request(original))
          })
        })
      }

      original._retry = true
      isRefreshing = true

      try {
        const res = await axios.post('/api/auth/refresh',
          { refreshToken: getRefreshToken() })
        if (res.data.code === 200) {
          setTokens(res.data.data.accessToken, res.data.data.refreshToken)
          pendingQueue.forEach(cb => cb())   // 放行排队的请求
          pendingQueue = []
          return request(original)
        }
        throw new Error('Refresh failed')
      } catch {
        clearTokens()                        // 刷新失败：清空，回登录页
        window.location.href = '/login'
      } finally {
        isRefreshing = false
      }
    }
    return Promise.reject(error)
  },
)
拦截器是什么？这个文件的设计思路

请求拦截器（request.use）：每个请求发出前都会先经过它。这里做的唯一一件事是"自动带上 Token"——业务代码里永远不用手动加 Header，登录态统一在这里处理。

响应拦截器（response.use）：每个响应返回前先经过它，做两件事：

  • 按 code 解包：code === 200 直接放行，业务层拿到的就是 res.data.data（真正的数据）；其他 code 统一弹错误提示并 reject。业务代码里不用写任何 if (res.code !== 200) 的重复判断。
  • 401 处理：Token 过期时后端返回 401。这里自动用 Refresh Token 换新，然后重放原请求——用户无感知。

为什么需要"并发去重"（isRefreshing + pendingQueue）？页面同时发出 5 个请求，Access Token 恰好全过期——5 个请求会同时收到 401。如果不加锁，就会同时发出 5 个 refresh 请求，浪费且可能冲突。正确做法：只让第一个 401 去刷新（isRefreshing 置 true），其余 4 个把自己的"重放函数"推进 pendingQueue 排队；刷新成功后统一放行，用新 Token 重放。这是双 Token 方案在真实项目里的标准写法。

刷新也失败怎么办？说明 Refresh Token 也失效了（比如用户被踢下线、Token 被吊销），清空本地 Token 跳回登录页——这是唯一需要用户重新登录的场景。

5.3 路由守卫 + 权限组件：前后端一致的权限模型

路由层用 ProtectedRoute 判断有没有 Token（没登录 → 踢到 /login）；页面内按钮用 Permission 组件判断权限码。权限码来自登录接口返回的 permissions 数组，超级管理员有通配符 *。

router/index.tsx（守卫核心）TSX
function ProtectedRoute({ children }: { children: React.ReactNode }) {
  const token = localStorage.getItem('cms_access_token')
  if (!token) return <Navigate to="/login" replace />
  return <>{children}</>
}

export default function AppRouter() {

前端为什么也要做权限？和后端权限什么关系？

权限有两层防线，缺一不可：

  • 后端（真正的安全边界）：@PreAuthorize 在接口层校验权限码。绕过前端直接 curl 接口，没有权限照样 403。安全永远以后端为准。
  • 前端（体验层）：没权限的菜单不显示、没权限的按钮不渲染。否则用户能看到"编辑"按钮，点一下弹"无权限"，体验极差。

所以前端权限是"藏入口"，后端权限是"拦请求"，两层配合才完整。

几个设计细节，为什么这么写？
  • Token 放 localStorage：刷新页面不丢登录态。相比 Cookie，JS 可读可写，能手动放进 Authorization Header。代价是有 XSS 风险时可能被偷——生产项目可升级为 httpOnly Cookie + CSRF 防护，本项目作为教学取舍用 localStorage。
  • <Navigate to="/login" replace />：React Router 的声明式跳转。replace 表示替换历史记录——用户按返回键不会回到被拦截的页面，避免"跳回死循环"。
  • ProtectedRoute 只查"有没有 Token"：不查 Token 是否有效（那是后端的事）。过期了怎么办？第一次请求会 401，被 5.2 的拦截器自动刷新兜住；刷新失败才被踢回登录页。这样路由层保持简单，不用自己解析 JWT。
  • Permission 组件用 children 包裹：<Permission permission="article:update"><Button/></Permission>——把"有权限才渲染"做成了声明式组件，业务代码里不用写 if/else。fallback 参数还能支持"无权限时显示别的占位内容"。

5.4 Zustand 状态管理：用户 / 权限 / 菜单

三个全局状态：user 当前用户、permissions 权限码数组、menus 菜单树。登录动作把所有状态一次灌满；hasPermission 支持通配符，是 Permission 组件的判据。

stores/auth.ts（结构）TS
export const useAuthStore = create<AuthState>((set, get) => ({

  login: async (username, password) => {
    const result = await authApi.login({ username, password })
    setTokens(result.accessToken, result.refreshToken)      // Token 落 localStorage
    set({ user: result.user, permissions: result.user.permissions || [] })
    await get().fetchMenus()                               // 拉菜单树
  },

  hasPermission: (perm) => {
    const { permissions } = get()
    if (permissions.includes('*') || permissions.includes('*:*')) return true
    return permissions.includes(perm)
  },
}))

// App 启动时：有 Token 就先拉用户信息和菜单，恢复登录态
export async function initAuth(): Promise<boolean> {
  const token = getToken()
  if (!token) return false
  try {
    await useAuthStore.getState().fetchUserInfo()
    await useAuthStore.getState().fetchMenus()
    return true
  } catch { clearTokens(); return false }
}
Zustand 是什么？为什么不用 Redux？

create<AuthState>((set, get) => ({...})) 是 Zustand 创建 store 的写法：

  • set：更新状态的方法，set({ user, permissions }) 触发所有订阅该状态的组件重新渲染。
  • get：读取当前最新状态，get().fetchMenus() 调 store 里另一个 action。为什么要用 get 而不是闭包变量？因为闭包里的状态可能是旧的，get 永远拿最新值。

选 Zustand 不选 Redux 的理由（本项目体量下的对比）：

  • 零样板代码：Redux 需要 action 类型、action creator、reducer、connect/mapStateToProps 一堆模板；Zustand 一个 create 就完了，全局状态就三个（user/permissions/menus），Redux 是杀鸡用牛刀。
  • 选择订阅：useAuthStore(s => s.hasPermission) 只订阅 hasPermission 这一个字段，其他字段变化不会触发该组件重渲染，性能自然好。
  • Hook 原生支持：直接在 React 组件里用 useAuthStore(...)，不需要 Provider 包裹（Redux 要 <Provider> 包全树）。

initAuth() 为什么单独拆出来？刷新页面时 localStorage 里还有 Token，但内存里的 store 是空的——需要重新拉用户信息、菜单树来"恢复登录态"。在 App 挂载时调用，返回 false 说明恢复失败（Token 已失效），前端就跳回登录页。这一步是"刷新不掉线"的关键。

5.5 页面开发范式：列表页三步走

所有管理页都是同一套模式：① 查询状态 + fetch → ② 表格列定义 → ③ 弹窗表单（新增/编辑复用）。照着下面这段骨架写，CRUD 页面可以直接套。

pages/article/index.tsx（页面骨架）TSX
export default function ArticleList() {
  const [data, setData] = useState<ArticleVO[]>([])
  const [total, setTotal] = useState(0)
  const [query, setQuery] = useState<ArticleQuery>({ page: 1, pageSize: 10 })
  const [editing, setEditing] = useState<ArticleVO | null>(null)
  const [drawerOpen, setDrawerOpen] = useState(false)
  const [form] = Form.useForm()

  // ① 列表加载：query 变化即重新请求
  const fetchData = async () => {
    const result = await articleApi.getList(query)
    setData(result.records)
    setTotal(result.total)
  }
  useEffect(() => { fetchData() }, [query])

  // ② 编辑回显：先 resetFields 再 setFieldsValue
  const handleEdit = (record: ArticleVO) => {
    setEditing(record)
    form.resetFields()
    articleApi.getById(record.id).then(full => {
      form.setFieldsValue({ ...full })   // 详情接口返回全字段（含 content）
      setDrawerOpen(true)
    })
  }

  // ③ 提交：编辑/新增走同一个函数
  const handleSubmit = async () => {
    const values = await form.validateFields()
    editing
      ? await articleApi.update({ id: editing.id, ...values })
      : await articleApi.create(values)
    message.success(editing ? '编辑成功' : '新增成功')
    setDrawerOpen(false)
    fetchData()
  }

  // 表格列 + Drawer 表单（略）...
  return (
    <>
      <Card className="cms-toolbar-card"> {/* 搜索区 */} </Card>
      <Card className="cms-table-card">  {/* <Table /> */} </Card>
      <Drawer forceRender ...>               {/* 编辑表单 */}
        <Form form={form} layout="vertical"> ... </Form>
      </Drawer>
    </>
  )
}
编辑回显的坑（真实踩过）：弹窗组件（Modal/Drawer）默认懒挂载内部 Form，如果 setFieldsValue 在弹窗还没打开时就执行，值会被丢弃。解法：弹窗加 forceRender 让 Form 始终挂载，回显先 resetFields() 再 setFieldsValue()，防止脏数据串场。
页面骨架里的每个 Hooks，逐个拆开讲
  • useState：组件级状态。const [data, setData] = useState([]) 声明"列表数据"状态；调用 setData(新值) 会触发组件重新渲染，页面自动更新。这就是 React 的"数据驱动视图"——不用手动操作 DOM。
  • useEffect(() => { fetchData() }, [query])：副作用钩子。[query] 是依赖数组——只要 query 变化（比如翻页、改搜索条件），fetchData 就重新执行。这就是"查询条件一变，列表自动刷新"的原理。依赖数组为空 [] 则只在挂载时执行一次。注意：不能写成 useEffect(() => fetchData()) 不传依赖——那每次渲染都会执行，且容易死循环。
  • Form.useForm()：antd 的表单实例。它脱离"受控组件"的繁琐（不用给每个 Input 绑 value/onChange），通过 form.setFieldsValue() 整体回填、form.validateFields() 统一校验取值。Form 组件用 form={form} 属性接收这个实例，两者绑定。
  • forceRender（Drawer 属性）：强制弹窗内部的 Form 在弹窗未打开时就挂载。没有它，Form 是在弹窗打开那一刻才创建的，而 setFieldsValue 在打开前就调用了——值被丢进一个还不存在的表单里。这是回显失败的根因。
  • 编辑时先 resetFields() 再 setFieldsValue()：resetFields 清空上一次编辑残留的值，再回填新值。否则上次编辑的字段会"串"到本次表单里（尤其是弹窗复用时）。
  • 新增/编辑复用同一个 handleSubmit：靠 editing 是否有值判断——有值走 update 并带上 id，没值走 create。一个函数两条分支，弹窗表单完全复用，省一半代码。

为什么 fetchData 用 async 函数但 useEffect 里调用时不 await？useEffect 的回调不支持 async（会报类型错误），所以要么在外面定义 async 函数再调用，要么用 IIFE。这里把 fetchData 定义成独立的 async 函数，既能在 useEffect 里触发，也能在提交成功后手动调用刷新列表（fetchData()），一处定义、多处复用。

下面 7 个问题都是开发过程中真实遇到并修掉的，每个都写了现象、根因和修复方式。

现象根因修复
1062 Duplicate entry 'admin' data.sql 重复执行，唯一键冲突 data.sql 开头按依赖顺序 DELETE 所有表 + 重置 AUTO_INCREMENT，变成可安全重复执行的幂等脚本
1062 Duplicate entry '31' for key 'PRIMARY' 按钮权限 INSERT 没指定显式 ID，自增到 31 与后面日志菜单显式 ID 31/32 撞车 所有按钮权限行显式指定 ID 段（101-105、111-114、201-204...），与核心菜单 ID 错开
登录报 Unsupported character encoding 'utf8mb4' JDBC URL 写了 characterEncoding=utf8mb4——该参数只接受 Java 标准字符集名 改为 characterEncoding=UTF-8（驱动自动映射 utf8mb4）；建表语句的 CHARSET=utf8mb4 不用动
登录一直 密码错误，admin/editor 都进不去 data.sql 里 BCrypt 哈希是无效占位符，对任何密码都不匹配 用 bcrypt 重新生成 admin123 的哈希（$2a$ 前缀、cost 10，与 Spring Security 默认一致）替换
编辑文章报 Column 'cover' cannot be null 前端表单没有 cover 字段（提交即 null）+ 后端 update() 没做 null 兜底，null 怼进 NOT NULL 列 前端补封面输入框与回显；后端 update() 对可空字段统一 != null ? x : "" 兜底
编辑弹窗回显为空 setFieldsValue 在弹窗未打开（Form 未挂载）时执行，配合 destroyOnClose 值被丢弃 弹窗加 forceRender，去掉 destroyOnClose；回显先 resetFields 再 setFieldsValue
Vite build 报 EPERM 删不掉 dist 沙箱/杀软阻止删除旧 dist 目录 vite build --emptyOutDir false 跳过清空，或手动删 dist
从这些坑里总结 3 条经验：① 初始化 SQL 必须能重复执行（幂等）；② 手写 SQL 的可空字段要做 null 兜底；③ 前端"弹窗 + 表单回显"要保证 Form 先挂载再赋值。
